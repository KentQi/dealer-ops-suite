# 复核协议（L6 LLM 语义复核）

本文件是给**执行复核的 LLM** 的操作手册，也是 L6 的判定与留痕契约。脚本只做结构校验与落盘，**不调用外部模型**；复核结论由当前 harness 的 LLM 负责。R1–R10 的清单文字以本文件与 `review_common.py` 为准，packet/report schema 保持不变。

## 交付时序

```text
load_master.py → 对应业务模式引擎 → 对账工作簿＋_结算结果.json＋_回写.json
  → 铺货可选 apply_v17.py（同步工作簿路径与哈希）
  → make_review_packet.py → 复核包（packet JSON / MD）
  → 当前 harness 的 LLM 按 R1–R10 复核 → 报告 JSON
  → apply_review.py --apply → NN-复核记录＋_复核记录/复核锁.json
  → apply_review.py --check → 「复核有效」
  → 交付 → writeback_ledger.py 先 dry-run、再 --write
任何一次工作簿保存 → 复核锁失效 → 必须重新生成复核包并重评
```

```bash
# 1) 生成复核包
python3 "$SKILL_DIR/scripts/make_review_packet.py" "<工作簿.xlsx>" \
    --cfg "<本期目录/RECON_CFG.json>" --master "<_主档.xlsx>" \
    --out "<复核包.json>" --md "<复核包.md>"

# 2) 由当前 harness 的 LLM 按 R1–R10 复核，产出报告 JSON（schema 见下）

# 3) 落盘（默认 dry-run；--apply 与 --check 互斥）
python3 "$SKILL_DIR/scripts/apply_review.py" "<工作簿.xlsx>" "<报告.json>" \
    --packet "<复核包.json>" --apply

# 4) 交付前校验；如指定过 --report-dir，这里也须传同一参数
python3 "$SKILL_DIR/scripts/apply_review.py" "<工作簿.xlsx>" --check
```

**无文件写权限的 harness**：跳过第 3/4 步，把复核包与报告 JSON 一并交给用户归档，并明确 verdict；不得声称「复核有效」。这种复核**不构成审计意见**。

## 结果凭证与复核包

schema 为 `dealer-ops/review-packet@1`，除 `generated_at` 外确定性输出。取不到的值写 `null` 并进 `warnings`，绝不臆造 0。复核时以 packet 为索引入口，**必须回工作簿、主档与源流水核对原文和数字**；缺失项按「不适用」处理并写明理由。

同目录存在 `_结算结果.json` 时，它是本期规则底稿：

- `workbook.path` 必须指向当前工作簿，`workbook.sha256` 必须等于当前文件哈希；否则生成复核包直接失败。
- 顶层 `business_type` 必须与 `rule_result.business_type` 一致，且只能是 `consignment` 或 `monthly_buyout`。
- `master` 与 `sources` 必须保存出账时绝对路径和 SHA-256；生成复核包时，当前主档及铺货 `jia/sales/inventory`、月结 `receipts/returns/sales` 必须与快照逐一相同。换主档、换源表或源表出账后变更均直接失败，禁止把旧 `rule_result` 拼到新文件哈希上。
- 铺货执行 `apply_v17.py` 后，应由脚本同步结果凭证的工作簿路径与哈希；不得手工修改凭证来绕过复核。
- 没有结果凭证时只允许历史标签扫描；`rule_result=null`、`priced_rows=[]` 并产生警告，不得冒充本期规则复算凭证。

| 字段 | 说明 |
|---|---|
| `schema` / `generated_at` | 版本标识 / ISO8601 生成时间 |
| `business_type` | `consignment`（铺货代销）/ `monthly_buyout`（月结买断）/ 历史模式可能为其他值或 `null` |
| `workbook{path,sha256,size}` | 被复核工作簿与哈希（复核锁基准） |
| `master{path,sha256}\|null` | 主档（传入时） |
| `sources[{role,path,sha256}]` | 铺货：`jia/sales/inventory`；月结：`receipts/returns/sales` |
| `period` / `asof` | `period={"start":"YYYY-MM-DD","end":"YYYY-MM-DD"}` 或 `null`；`asof` 为日期字符串或 `null` |
| `sheets[{name,rows,cols}]` | 工作簿结构 |
| `figures` | 关键数索引；共同字段含 `opening_qty/opening_amount/settled_qty/settled_amount/diff_qty/diff_amount/addback_qty/addback_amount/tiehua_total/period_end`；不适用字段为 `null` |
| `rule_result` | 引擎的完整规则结果；铺货含 `priced_lines/quantity_reconciliation`，月结含 `priced_receipts/priced_returns/priced_sales_for_decal` |
| `sku_rows` | SKU 汇总；铺货另含理论期末、库存、回加、实际结存、盈亏与状态；月结另含签收、退货及仅用于贴花的动销量 |
| `priced_rows` | 逐笔货款底稿：流水号、日期、条码、数量、单价、金额与 `price_evidence`；月结按签收／退货分角色 |
| `tiehua_rows` | 逐笔贴花底稿；铺货含销售／退货，月结含乙方动销／退货冲减 |
| `claims[{sheet,cell,text,numbers[]}]` | 文字断言句及其中数字 |
| `cross_refs[{sheet,cell,text,refs[]}]` | 「详见附表 NN」类交叉引用 |
| `contract` | 可含 `no/method/basis/objection_days/signback_days/pay_day_text/buyout_date/payment_due_date`，未取到为 `null` |
| `redline_scan[{id,pattern,hits}]` | 红线措辞扫描；命中只报告，不自动下结论 |
| `checklist[{id,item}]` | R1–R10 清单 |
| `warnings[]` | 取数缺失、歧义与凭证提示 |

铺货 `figures.settled_amount` 是销售货款减退货冲减后的金额；只有本期单次授权时才另含盈亏。`figures.diff_amount` 始终是盈亏列示金额，不代表已纳入总额。月结 `opening_qty/opening_amount/diff_qty/diff_amount` 必须为 `null`，不能把写回用 operational zero 当作 BIP 期初或库存盈亏。

## 报告 JSON 结构

schema 为 `dealer-ops/review-report@1`：

| 字段 | 说明 |
|---|---|
| `schema` | 固定 `dealer-ops/review-report@1` |
| `reviewer{name,model}` | 复核人 / 模型标识 |
| `reviewed_at` | 带时区的 ISO8601 |
| `workbook_sha256` | 必须等于当前工作簿及 packet 的工作簿哈希 |
| `period` | 期间，可为 `null` |
| `verdict` | `通过` / `有条件通过` / `不通过` |
| `checklist[{id,result,note}]` | R1–R10 全覆盖；result ∈ `通过` / `不通过` / `不适用` |
| `findings[{level,category,sheet,cell,claim,evidence,suggestion}]` | level ∈ `阻断` / `警告` / `提示`；evidence 必须给具体数字或原文 |
| `summary` | 结论摘要；`不通过` / `有条件通过` 必须非空 |

脚本强制：

- 工作簿哈希不一致 → 拒绝；
- checklist 缺 R1–R10 任一项 → 拒绝；未知 id → 警告；
- 任一清单项为 `不通过` ⇒ verdict 不得为 `通过`；
- 存在 `阻断` finding ⇒ verdict 必须 `不通过`；
- 无阻断但有 `警告` finding ⇒ verdict 不得为 `通过`；
- `不通过` / `有条件通过` 的 summary 必须非空；
- `--apply` 必须提供 `--packet`，并核对报告与 packet 的期间、工作簿身份；无包报告只能 dry-run／人工归档。

## R1–R10 操作手册

### R1 按业务模式复算数量勾稽与逐笔金额（铺货代销／月结买断）

- **铺货**：逐 SKU 核对 `净动销＝销售－退货`、`理论期末＝本次 BIP 期初－净动销`、`实际结存＝库存导出＋回加`、`盈亏＝理论期末－实际结存`。逐笔核对正常销售数量 × 销售日合同价、退货数量 × 原销售价，金额合计与 `rule_result` 和工作簿一致。
- **月结**：逐 SKU 核对 `买断数量＝本期签收－本期退货`。逐笔核对签收数量 × 签收日合同价、退货数量 × 原签收价；乙方动销量不得减少买断货款。
- 共同核对：流水号唯一、业务日期属于本期、价格在该业务日唯一生效；金额偏差 > 0.01 元、数量不等或取价依据不符 → **阻断**。
- 不要求 BIP 期初等于上期期末；不检查任何旧货值恒等式，不用调价价差倒挤。

### R2 合计=明细之和（对账说明、对账单与明细表跨表一致）

- 核：00/01 的结算、退货、盈亏列示、贴花与 02/05/06/07 及 packet 明细一致；月结签收、退货、买断、动销贴花各指标使用对应来源。
- 同一指标跨表必须同值；明细之和与合计不符 → **阻断**。缺库存的铺货 SKU 不得按库存 0 纳入盈亏合计。

### R3 贴花独立复算（铺货期末标准与退货原标准／月结逐笔动销日标准）

- **铺货**：正常销售按对账期末日标准；退货仅当原销售已计提时按原销售标准冲减，未计提不冲，无法确认必须阻断。盈亏不参与贴花。
- **月结**：乙方动销按每笔动销日标准；退货按原销售是否计提及原标准处理。动销贴花与签收货款相互独立。
- 核：数量 × 标准 = 金额，合计 = 明细之和，非结算商品不参与；同条码同日多标准、缺标准或版本取错 → **阻断**。

### R4 退货原价、盈亏列示与单次授权／月结签收净额分列正确

- **铺货**：退货数量本期冲减，金额按原销售价；缺原流水或明确原价不得按退货日价格替代。任何非零盈亏均列示，正短缺、负盘盈，按期末合同价计算列示金额。
- 盈亏默认不进入结算总额。若纳入，授权须 `approved=true` 且 `period_start/period_end` 与本期完全一致；不继承、不取绝对值。未纳入时 `settlement_amount=sales_settlement_amount`，纳入时才加有符号的 `variance_display_amount`。
- **月结**：签收货款、退货冲减、买断净额与动销贴花分别列示，退货按原签收价；不得把乙方动销当作货款减项，也不得虚构 BIP 期初或库存盈亏。
- 原价无依据、授权跨期／缺期、符号错误或分列混淆 → **阻断**。

### R5 文字断言与数据一致（结论句中的数字、SKU 数、件数）

- 查：00「主要结论」、01「对账说明」、02「差异结论」及月结对应结论区；按标题定位，不猜固定行号。
- 核：金额、件数、SKU 数、百分比与表内实算一致；短缺／盘盈措辞与符号一致；月结不得出现铺货期初或盈亏结论。
- 判据：断言与数据不符 → **阻断**。

### R6 交叉引用真实存在（「详见附表 NN」确有该数）

- 查：packet `cross_refs` 与正文。
- 核：被引用附表存在且有对应数值或明细，编号未错位。
- 判据：指向不存在或数字不符 → **警告**；若引用的是关键金额 → **阻断**。

### R7 口径披露完整（期间、BIP 期初或签收来源、非结算商品、盈亏是否纳入）

- 核：流水覆盖期间与缺日已写明；铺货明确期初来自本次甲方 BIP，月结明确货款来自签收与退货；非结算商品已排除并披露；盈亏是否纳入及授权期间明确；`asof` 与库存／数据基准日一致。
- 月结的买断日和付款截止日分别披露，不把其中任一日期默认成另一日期。
- 判据：缺任一项 → **警告**；关键来源、期间或金额口径缺失且可能误导 → **阻断**。

### R8 红线检查（不作归因、不称实盘、不臆断税率、贴花兑付不替用户决定等）

- 查：packet `redline_scan` 命中项及全文措辞。
- 核：不归因乙方漏报／故意／责任；系统库存不称「实盘」；税率以实际开票资料为准；贴花兑付由双方书面确认；金额右对齐、保留两位小数。
- 判据：归因、实盘、臆断税率 → **阻断**；格式类 → **警告**。命中词不等于违规，必须看上下文。

### R9 合同条款与主档/合同原文一致（业务类型/基数/异议期/签回期/买断日/付款截止日）

- 核：合同编号、业务类型、结算基数、价格附件、异议期、签回期与主档及合同原文一致；月结的买断日、付款截止日分别一致。
- 主档缺项只能明确标注「主档未登记，以合同为准」，不得印演示值或默认付款日。
- 判据：条款与合同不符 → **阻断**；占位但未标注来源 → **警告**。

### R10 异常与差异解释充分（任何盈亏均列出并供双方核对，未编造原因）

- 核：所有盈亏 SKU、件数与列示金额均列出；短缺／盘盈符号清楚；缺库存、缺条码、未建档、价格断档、负净额等异常有阻断记录或待办。
- 任何盈亏均可出单，不设差异率阈值；原因只能写「待双方核对」，不得编造责任或成因。
- 判据：编造原因 → **阻断**；盈亏未列示或说明不充分 → **警告**；故意隐瞒非零盈亏 → **阻断**。

## 判定与阻断

| 情形 | verdict |
|---|---|
| 存在 ≥ 1 条 `阻断` | 必须 `不通过` → **不得交付** |
| 无阻断、存在 ≥ 1 条 `警告` | 只能 `有条件通过`，summary 写明条件与责任方 |
| 无阻断、无警告（或仅提示） | `通过` |

- **不通过**：修正数据 → 重新出账 → 重新生成复核包 → 重评；不能只改报告。
- **有条件通过**：交付前把条件明确告知用户并留痕。

## 留痕与哈希绑定

- 复核表按实际工作表数量命名为 `NN-复核记录`；兼容历史 `08/09/10-复核记录`。记录复核人、模型、时间、结论、被复核哈希、报告名、R1–R10、findings 与免责声明。
- `<工作簿目录>/_复核记录/` 保存报告 JSON 与同内容 MD；`复核锁.json` 含 `{pre_sha256,post_sha256,verdict,report,applied_at}`。
- `--check` 要求复核表与锁存在、pre 哈希一致、当前工作簿哈希等于 post 哈希，且 verdict 为「通过」或「有条件通过」；全满足才打印「复核有效」。
- 任何保存（含手工另存）都会改变哈希并使锁失效，必须重评，不得手工造锁或删锁。
- `--apply` 幂等；不通过时只归档报告、不写复核表、不改工作簿，退出码 1。
- 默认 dry-run 对任何报告只打印计划并返回 0；只有 `--apply` 才真正落盘，且必须携带有效 `--packet`。
- `writeback_ledger.py --write` 只接受 `_结算结果.json` 绑定的 `_回写.json`，逐字段比对内嵌 `writeback`，并要求目标主档路径及当前哈希等于出账快照。锁的 `pre_sha256` 须等于出账工作簿哈希，当前工作簿哈希须等于 `post_sha256`，归档报告与锁的 schema、被复核哈希及 verdict 一致。无锁、换值、换主档或复核后改工作簿均阻断；首次写入后的完全相同重复操作可幂等 noop。

## 外部工作簿复核（无复核包）

只有工作簿、没有复核包时：用 `openpyxl` 读全部单元格与合并区（公式读原式，不读缓存值），按 R1–R10 直查；输出同 schema 报告供人工归档，不写复核表、不声称「复核有效」。这种复核**不构成审计意见**。
