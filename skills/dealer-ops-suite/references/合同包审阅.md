# 合同包审阅与放行协议

合同包＝主合同＋防窜货附加协议＋价格／出货政策。审阅分确定性与 LLM 语义两层，不能互相替代；写前预检与最终放行又是两道不同的门。

## 1. 两层审阅

### 确定性审阅

`review_contract_package.py` 检查必填、格式、日期、金额、比例、目标、保证金、附件日期与价格政策。`check_policy.py` 允许同码多版本合法并存，但阻断缺价、非法值、缺生效日和区间重叠；断档及业务歧义须确认。

### LLM 语义审阅

当前模型必须阅读三份原文，检查：

1. 主体、合同编号、期限、产品范围、结算方式是否跨文件一致；
2. 价格、贴花、返利、保证金、账期、指标之间是否矛盾；
3. 价格有效期是否覆盖合同期，月中调价是否有明确生效日；
4. 月度／季度指标、返利触发与未达成后果是否清楚；
5. 防窜货罚则、举证、认定程序与主合同是否衔接；
6. 验收、退换、交付、续约、解除、库存与价款处理是否完整；
7. 歧义词、单方义务、罚则基数与上限、争议解决是否明确。

每条 finding 必须有“文件＋条款号＋原文”。只写“需确认／可能风险”，不出法律意见，不直接改合同，不编造问题。

```json
{
  "findings": [
    {
      "category": "合同包一致性",
      "severity": "high",
      "field": "第七条",
      "label": "季度指标",
      "message": "主合同与政策附件的指标口径不一致。",
      "evidence": {"document": "主合同", "clause": "第七条", "quote": "原文……"},
      "ask": "请确认以哪一份为准并同步修改。"
    }
  ]
}
```

## 2. 严重度与处理

| 级别 | 含义 | 处理 |
|---|---|---|
| `blocker` | 客观缺失、非法值或矛盾 | 修正后重跑；不得写入或放行 |
| `high` | 可能改变权利义务或结算结果 | 按 finding id 登记处理后才可继续 |
| `medium` | 表述或覆盖提醒 | 告知并留痕 |
| `low` | 建议项 | 可延后，不静默丢弃 |

高风险处理文件：

```json
{
  "C-001": {"status": "已修正", "note": "主合同与附件已统一", "owner": "责任人"}
}
```

状态限`已修正／接受风险／不适用`，说明与责任人不得为空。无关 finding id 也会阻断。

## 3. 写前预检：`--approve-write`

```bash
python3 "$SKILL_DIR/scripts/review_contract_package.py" \
  --spec "$SKILL_DIR/scripts/spec/jx.json" --values "<主合同-values.json>" \
  --fc-spec "$SKILL_DIR/scripts/spec/fc.json" --fc-values "<附件-values.json>" \
  --policy "<价格政策.xlsx>" --llm-findings "<llm-findings.json>" \
  --resolutions "<高风险处理.json>" --approve-write \
  --out "<写前审阅.json>" --md "<写前审阅.md>"
```

此阶段验证：审阅 schema、LLM 已合并、blocker 为 0、high 处理完整、findings 指纹未变。**不读取成品哈希**，因此不会形成“尚无成品却要求成品哈希”的死锁。凭证的 `input_files` 另绑定 `spec / values / fc_spec / fc_values / policy` 五类输入的绝对路径与 SHA-256，审阅后任何输入变化都会使凭证失效。

`apply_fill.py --review <写前审阅.json>` 为必需参数，并核对本次 `--spec`、`--values` 正是写前审阅绑定文件，不能用甲合同凭证填乙合同数值。没有写前凭证、LLM 未合并、处理记录不完整或输入哈希变化，均不写任何内容。

## 4. 最终放行：`--release`

成品形成后，用同一组确认值、findings 与处理记录生成最终凭证：

```bash
python3 "$SKILL_DIR/scripts/review_contract_package.py" \
  --spec "$SKILL_DIR/scripts/spec/jx.json" --values "<主合同-values.json>" \
  --fc-spec "$SKILL_DIR/scripts/spec/fc.json" --fc-values "<附件-values.json>" \
  --policy "<最终价格政策.xlsx>" --llm-findings "<llm-findings.json>" \
  --resolutions "<高风险处理.json>" --release \
  --main-file "<最终主合同.docx>" --fc-file "<最终防窜货附件.docx>" \
  --out "<最终审阅.json>"
```

三份成品文件必须不同且可读取。凭证记录成品绝对路径、SHA-256、findings 指纹与高风险处理结果，同时保留五类审阅输入的 `input_files` 路径与哈希；独立 `--verify-release` 和最终 `verify_fill.py` 都会重新校验这些输入未变。

```bash
# 独立复核三文件当前哈希
python3 "$SKILL_DIR/scripts/review_contract_package.py" --verify-release "<最终审阅.json>"

# 主合同最终验收：还检查 --result 是否正是放行主合同
python3 "$SKILL_DIR/scripts/verify_fill.py" \
  --template "<原始主合同模板.docx>" --result "<最终主合同.docx>" \
  --plan "<全量-plan.json>" --spec "$SKILL_DIR/scripts/spec/jx.json" \
  --values "<主合同-values.json>" --review-release "<最终审阅.json>"
```

放行后替换主合同、防窜货附件或价格政策中的任意一份，哈希都会失效；更换 `--result` 为另一份主合同也会失败。修正后必须重新审阅、重新放行、重新验收，不手改凭证。

## 5. 责任边界

- 未提供文件写“未覆盖”，不能说“没问题”。
- 找不到问题写“未发现”，不能编造风险凑数。
- 用户未确认高风险处理，不算通过。
- 合同审阅不是法律意见；最终哈希一致只证明文件未变，不证明条款合法或商业合理。
