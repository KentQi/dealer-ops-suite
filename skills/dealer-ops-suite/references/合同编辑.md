# 合同无损编辑与交付

本文件承接 `SKILL.md` 的合同路由。目标是把用户确认值写进主合同与防窜货附件，同时保证模板、条款和格式不被越界修改。

## 1. 硬边界

1. 只写 `values.json` 中用户明确确认的值；不推断目标、返利、保证金、账期、违约金或其他实质条款。
2. 不增删段落、表格、行、列、附件或签章位，不改标题、编号、样式、字体和页边距。
3. 甲方固定信息只校验不修改；附件违约金标准表在 `spec.locked_content` 登记了标准版时只校验不修改（公开版未登记，验收单显式披露「未登记」）。
4. 原始模板只读，成品必须另存；硬链接指向模板也禁止。
5. 有 `editor_sdk`／`doc_*` 无损编辑能力时必须使用该通道；没有时明确能力边界，不用 python-docx 强改成品。
6. `apply_fill.py` 必须带有效 `--review`；`verify_fill.py` 必须带有效 `--review-release`。两道门不可互相替代。

## 2. 输入与一次性确认

适用规格：`scripts/spec/jx.json`、`dx.json`、`fc.json`。字段见 [field-map.md](field-map.md)，确认页结构见 [confirm-template.md](confirm-template.md)。

```bash
python3 "$SKILL_DIR/scripts/scan_blanks.py" \
  --spec "$SKILL_DIR/scripts/spec/jx.json" --doc "<原始主合同模板.docx>" \
  --json-out "<scan.json>"
```

- `定位失败 > 0` 或出现未登记空白：模板可能改版，停止，不自行套用。
- 一次性列出必填、非必填、格式和示例；用户只补了一部分时，再一次列清全部缺口。
- 从营业执照、旧合同或 Excel 提取的值必须逐项回显确认。
- `values.json` 始终是**累积全量**，纠错或补填不能换成只有增量的值文件。

## 3. 编译可信计划

```bash
python3 "$SKILL_DIR/scripts/build_plan.py" \
  --spec "$SKILL_DIR/scripts/spec/jx.json" --doc "<原始主合同模板.docx>" \
  --values "<主合同-values.json>" --out "<全量-plan.json>"
```

- 失败时只可能留下 `.rejected` 排查文件，不得执行。
- `plan.json` 只能由脚本生成，不手工编辑；写入与验收都会用 `spec＋values＋原始模板`重编译核对。
- 把“入参 → 落笔”对照表交给用户确认，并与原始确认消息一并归档。
- 本地脚本只能证明“成品＝计划＋确认值”；values 与 spec 的变更仍须靠用户确认记录约束。

## 4. 写前合同包审阅

按 [合同包审阅.md](合同包审阅.md) 完成确定性与 LLM 两层审阅。三份文件都必须覆盖：主合同、防窜货附件、价格／出货政策。

```bash
python3 "$SKILL_DIR/scripts/review_contract_package.py" \
  --spec "$SKILL_DIR/scripts/spec/jx.json" --values "<主合同-values.json>" \
  --fc-spec "$SKILL_DIR/scripts/spec/fc.json" --fc-values "<附件-values.json>" \
  --policy "<价格政策.xlsx>" --llm-findings "<llm-findings.json>" \
  --resolutions "<高风险处理.json>" --approve-write --out "<写前审阅.json>"
```

`--approve-write` 只检查结构与处理记录，不要求成品哈希。`blocker` 必须修正；`high` 必须按 finding id 提供：

```json
{
  "C-001": {"status": "已修正", "note": "已同步修改第七条", "owner": "责任人"}
}
```

状态只能是 `已修正／接受风险／不适用`。`medium/low` 仍需告知用户。

## 5. 无损写入

1. 将模板复制为新的输出文件，并留 `.bak`。
2. 用当前 harness 的展示能力打开输出文件，从编辑器池取该路径对应的 `file_id`。
3. 执行：

```bash
python3 "$SKILL_DIR/scripts/apply_fill.py" \
  --plan "<全量-plan.json>" --edsdk "<editor_sdk>/edsdk.py" --file-id "<file_id>" \
  --protect "<原始主合同模板.docx>" --spec "$SKILL_DIR/scripts/spec/jx.json" \
  --values "<主合同-values.json>" --review "<写前审阅.json>"
```

脚本先检查写前审阅、计划可信性和目标文件身份，再解析全部定位并从后往前写。定位失败、区间冲突、重复执行、写错实例或保存读回失败均中止。

中途失败必须完整回滚：

```bash
cp "<输出.docx>.bak" "<输出.docx>"
python3 "<editor_sdk>/edsdk.py" call close_file file_id=<file_id>
```

随后重新打开展示并取得**新的** `file_id`。只恢复磁盘而复用脏内存实例，可能把错误内容再次写回。

## 6. 最终放行与验收

成品形成后，以同一组 findings 和高风险处理记录生成最终三文件凭证：

```bash
python3 "$SKILL_DIR/scripts/review_contract_package.py" \
  --spec "$SKILL_DIR/scripts/spec/jx.json" --values "<主合同-values.json>" \
  --fc-spec "$SKILL_DIR/scripts/spec/fc.json" --fc-values "<附件-values.json>" \
  --policy "<最终价格政策.xlsx>" --llm-findings "<llm-findings.json>" \
  --resolutions "<高风险处理.json>" --release \
  --main-file "<最终主合同.docx>" --fc-file "<最终防窜货附件.docx>" \
  --out "<最终审阅.json>"

python3 "$SKILL_DIR/scripts/verify_fill.py" \
  --template "<原始主合同模板.docx>" --result "<最终主合同.docx>" \
  --plan "<全量-plan.json>" --spec "$SKILL_DIR/scripts/spec/jx.json" \
  --values "<主合同-values.json>" --review-release "<最终审阅.json>"
```

最终门禁先重新计算主合同、防窜货附件和价格政策 SHA-256，并确认 `--result` 是凭证绑定的主合同；然后检查：

1. 全量计划重编译与值指纹；
2. 计划外文本改动；
3. 字符格式、结构属性、分节与纸张；
4. 段落、表格、文本单元数量；
5. 页眉页脚、文本框和域代码；
6. 必填完整性、甲方固定信息、锁定条款表；
7. 残留占位符；
8. 样式、编号、文档属性；
9. DOCX 包部件清单、非正文部件语义哈希与正文结构骨架。

只有退出码 `0` 可交付。`1` 为越界或凭证无效，`2` 为仍有占位符，`3` 为必填未完成；后两者也不是通过。

## 7. 纠错与二次补填

1. 把变更合并进累积全量 `values.json`，基于**原始模板**重新编译全量计划。
2. 可将本次变化的 op 摘成增量 `fix.json` 给 `apply_fill.py`，但仍须带 `--review`、`--protect`。
3. 更新写前审阅及最终放行凭证；最终用新的全量计划和最终凭证运行 `verify_fill.py`。
4. 验收基准永远是原始模板＋累积全量计划，不能拿上一轮成品当模板洗白历史越界。

附件与主合同分别成文、分别归档。任何成品变化都要重新生成最终放行凭证，旧哈希不得沿用。
